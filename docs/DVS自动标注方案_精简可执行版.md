## 1. 为什么原方案读起来费劲

不是你的问题，是文档结构的问题。四个具体原因：

| 现象 | 实质 |
|---|---|
| 大部分章节讲"如果没有真值怎么办" | 你有真值。路线 B（RGB 检测+跟踪+插值）整章与你不相干 |
| 花大篇幅讲 RGB→DVS 坐标转换 | 你的 DVS 与 RGB **同位、同分辨率、同 FOV**（`sensors.py` 共用同一 `transform`），像素坐标系完全相同，不需要任何转换 |
| 目录结构（§11.1）与现有 `sequences/` 布局冲突 | 按它改要重写采集器；正确做法是在现有结构上增量 |
| 五个状态字段（visibility/difficult/ignore/low_event/quality_flags）只给定义不给判定顺序 | 落地时无法编码。需要一张判定表 |

一句话：**把它砍到 1/3，再补上它漏掉的 4 件事，就是可执行方案。**

## 2. 已经验证成立的三件事（好消息）

这些我用你已有数据逐项实测过，是后续工作的地基：

### 2.1 3D 框投影几何正确

把 `annotations.json` 的框直接画到 RGB 和事件帧上（`_check_render.py` 可复现）：

- RGB 上近处车辆的框（救护车、右转黑车、中景三辆车）**贴合准确**；
- 事件帧上框与红蓝事件簇**位置一致**，目标轮廓可辨；
- 说明 `labels.py` 的针孔投影 + `get_inverse_matrix()` 用法没问题。

### 2.2 事件窗口与标签时刻严格因果对齐

实测 `sequence_000001/cam_01` 全部 1800 帧：

| 指标 | 实测值 |
|---|---|
| 每帧事件时间跨度 | 恒为 50 000 µs（`t_k` − 50 ms 到 `t_k`） |
| 帧内最后一个事件 − 帧时间戳 | 中位数 0 µs，最大 +2 µs |
| 帧内第一个事件 − 帧时间戳 | 中位数 −50 000 µs，最小 −50 001 µs |

也就是说 `W_k = [t_k − ΔT, t_k)` 这个因果窗口**在你的数据里是精确成立的**，标签就是窗口结束时刻的真值，不需要再做时间补偿。这是原方案 §7 要求的东西，你已经天然满足。

### 2.3 事件窗口索引可直接从 HDF5 取

`/frames/event_offsets` 长度 1801（首元素 0），第 k 帧区间就是 `offsets[k] : offsets[k+1]`。原方案要求的 `event_start_index / event_end_index` 不需要额外存储，导出时算一下即可。

## 5. 精简后的标注架构

原方案是"两条路线并行"。你的情况只有一条主线：

```
【采集时：记录不可再生信息 + 算完需像素信息】
  CARLA world
    ├─ 每个 tick 读全部 actor 的 3D box + 蓝图 ID + 位姿 + 速度
    ├─ instance segmentation 取可见像素 → visible_px / visible_bbox（分割图立即丢弃）
    └─ 写入 snapshot.json（约 22 MB/序列）——不写入成品框

【离线：投影】  ← 可反复重跑，不必重采
  snapshot.json + 相机内参
    ├─ 查显式蓝图映射表 → car / motorcycle / pedestrian / ignore
    ├─ 投影到 DVS 相机（= 投影到 RGB，二者像素系相同）
    └─ 写入 annotations.json（DVS 坐标，per frame 多实例）

【离线步骤 1：事件统计】（新增，纯读已有文件）
  events.h5 + annotations.json
    → 每实例：event_count / density / active_pixel_ratio / on_off_ratio
    → 每实例：quality_flags（low_event / static / tiny / severe_occlusion）

【离线步骤 2：质检与可视化】（新增）
  → RGB + 事件帧 + 框 三栏视频，按序列输出
  → 自动检查 6 项，失败即报警

【离线步骤 3：划分与统计】（新增）
  → 按路口/天气/时段分 split，禁止按帧随机分
  → 每类实例数、轨迹数、尺寸分布、低事件比例
```

### 5.1 标注时机：哪些必须在线，哪些离线

**结论：不要按"先采后标 / 边采边标"二选一，而是按"信息是否可再生"切分。** 判定标准只有一条——这条信息在序列落盘之后，还能不能从磁盘文件里算出来。

| 信息 | 采完还能重算吗 | 应在哪一步 |
|---|---|---|
| actor 的 `blueprint_id` | 否 | **采集时记录** |
| actor 逐帧位姿 / 3D 框 | 否（除非存快照） | **采集时记录** |
| 可见度 / 遮挡 | 否，需要逐像素信息 | **采集时算完，只存统计量** |
| 2D 投影框 | 能（只要有位姿快照） | 离线算 |
| 框内事件数 / 密度 / 极性比 | 能 | 离线算 |
| `low_event` / `difficult` 分级 | 能 | 离线算 |
| 质检视频、统计、train/val/test 划分 | 能 | 离线算 |

**三个不能纯离线的理由：**

1. CARLA 真值只存在于仿真进程里，序列采完就只剩 `annotations.json` 一个记录。**你已经踩到这个坑**：`blueprint_id` 没落盘，5 条序列（66 GB）无法回溯成三类别。
2. 可见度必须在线。分割图 / 深度图是逐像素的，采集时没开传感器，事后永远拿不到。
3. "用同一个 seed 重跑一遍再补采"理论上可行、实际不可靠：Traffic Manager、物理引擎、CARLA 版本任一变化都会造成漂移；而且成本等于全程仿真（实测约 15 分钟 / 90 秒序列）。

**两个不能纯在线的理由：**

1. 投影 bug 会被固化进数据。你现在已经踩到：`truncated` 语义错误、类别映射错误，修完都得重采。
2. 标注策略一定会迭代（ΔT 选择、困难样本阈值、静止目标取舍），每迭代一次就重采一轮是不可承受的。

**关键设计：存"快照"而不是"成品"**

采集时每帧写一份 `snapshot`：`actor_id`、`blueprint_id`、3D 框 extent、位姿（loc + rot）、速度、相机位姿、时间戳、可见像素数、可见区域紧框。**投影放到离线做。** 这样投影代码出 bug 时，重跑一个脚本（分钟级）即可，不必重跑仿真。

- 成本：120 actor × 1800 帧 × 约 100 B ≈ **22 MB / 序列**，相对 13 GB / 序列可忽略。
- 例外：可见度仍必须在线算完——分割图本身直接丢弃，只保留每个 actor 的可见像素数与紧框。
- 最小改动方案：保留现有在线投影不动，**额外 dump 一份 `snapshot.json`**。既不影响当前流程，又保留离线重投影能力。

### 5.2 时间窗口：建议改按 40 Hz 采集

原方案 §7.2 要求"比较 ΔT = 20/30/50/100 ms"，但你现在的标签只在 20 Hz 帧边界存在，**没法做这个对比实验**。

解决办法：**按 40 Hz 采集**（ΔT = 25 ms），标签每一帧都有真值。做实验时：

- 25 ms 窗口 → 直接取单帧；
- 50 ms 窗口 → 合并相邻 2 帧事件，标签取第 2 帧；
- 100 ms 窗口 → 合并 4 帧。

三种窗口全部有真值支撑，不需要伪造插值。事件总量不变（同样的物理事件），只是帧索引更密；RGB 仍按 20 Hz 落盘即可。

### 5.3 判定顺序（原方案缺的那张表）

**先明确"只标移动目标"的两层含义**，否则过滤规则会写错：

| 层面 | 规则 | 性质 |
|---|---|---|
| 类别层面 | 只标 `car` / `motorcycle` / `pedestrian`；自行车、路牌、静止设施一律不标 | **硬过滤**，采集时就排除 |
| 状态层面 | 属于三类别但当前帧静止（红灯前的车、站着的人）**仍写标签**，打 `stationary=true` + `low_event` | **软标记**，由加载器按配置决定 |

状态层面不硬删的理由：红灯停着的车重新起步时会产生事件，检测器在现场仍应识别它；但在纯事件相机下它当前帧确实可能零事件。这是实验配置问题，不是采集时删除的问题——标签保留、索引保留，参与与否交给加载器（建议默认排除主训练，另存一组做消融）。

顺带说明：这一条正好解决 §3 提到的行人堆叠问题——那 39 个静止堆叠行人会被整体标记并默认排除。

对每个投影成功的目标，按顺序判定，**先命中先定级**：

| 顺序 | 条件 | 结果 |
|---|---|---|
| 1 | 投影后无有效面积 / 完全在图像外 | 丢弃，不写 |
| 2 | 蓝图映射为 `ignore`（自行车、未知资产） | 写 `ignored_annotations[]`，记 reason |
| 3 | `visibility < 0.05` | 丢弃或 `ignore=true` |
| 4 | `visibility < 0.20` | `difficult=true`, `occluded=true` |
| 5 | 框被图像边界截断 | `truncated=true` |
| 6 | 框面积 < 400 px² | `difficult=true`, flag `tiny` |
| 7 | `stationary=true` 且框内事件 < 阈值 | flag `low_event` / `static` |
| 8 | 其余 | 正常主训练样本 |

`ignore=true` 与 `low_event` 的样本**保留在文件里**，由加载器按配置过滤——不要采集时删掉，否则会丢掉真实背景分布。

## 6. 场景设计修正（比标注本身更影响成败）

原方案通篇假设"数据里有三类目标"。你现在的数据里**实际只有一类可用**。需要的改动在 `traffic.py`，不在标注代码：

### 6.1 行人生成（必修）

现状：`world.get_random_location_from_navigation()` 全城随机撒 40 个行人，落到路口视场内的概率极低；实测 39 人叠在同一点、速度 0、永不移动。

修正：

1. 以机位组 `location.junction_center_m` 为中心，半径 30–60 m 内取 `Sidewalk` 类型 waypoint 作为出生点；
2. 目标点取同一侧人行道 15–40 m 外的 waypoint，保证行走路径穿越相机视场；
3. 生成后空跑 60 tick（约 1.5 s），检查位移 < 0.5 m 则重设目标点或销毁重生——阈值必须按行人步速定，正常步速这段时间能走 1.2~2.7 m，原地不动的才是 0 m；用「20 tick / 1 m」会把正常行人全判成卡住；
4. 单独生成一批"横穿人行横道"的行人：起点/终点取 crosswalk 的**长边**（横跨马路的那一段，8~14 m），往返运动；`Map.get_crosswalks()` 的顶点按文档给的"闭合多边形、首点重复"还原成一条条横道，取对角线会斜穿马路、取短边是沿路走；
5. 采集结束统计每机位可见行人轨数与平均位移，写入 `meta/`，作为数据验收项。
6. **拿不到路口坐标时不得退回 `get_random_location_from_navigation()`**：该原生导航调用在 Windows 客户端上会栈溢出（exit `0xC00000FD`）直接崩掉整个采集，而且撒出来的行人在相机视野外根本拍不到。应改用第一台相机的位置当中心，并在 rig YAML 里补齐 `location.junction_center_m`。
7. **行人不得用 `controller.ai.walker` / `go_to_location`**：那条路径要走导航网格（`Nav/TownXX.bin`），Town03 的导航数据不完整，服务端的路径搜索会一路递归到爆栈（同样是 exit `0xC00000FD`）。改用 `carla.WalkerControl` 直接推人走，方向自己算，每个 tick 前推一次。
8. **Town03 没有人行道 waypoint**（没有车道级 OpenDRIVE 数据，`generate_waypoints` 取不到 `Sidewalk` 类型），站位来源降级为：人行道 waypoint → 人行横道 → 地图出生点。

### 6.2 摩托车比例（必修）

从 `library.filter("vehicle.*")` 里按蓝图 ID 显式分成三组，按目标比例抽取（建议 car : motorcycle = 7 : 3），**并把自行车蓝图从生成列表剔除**（`vehicle.bh.crossbike` / `vehicle.diamondback.century` / `vehicle.gazelle.omafiets`），因为它们不属于三类别，混进去只会制造 ignore 污染。

### 6.3 类别映射表（显式清单，禁止子串猜测）

```yaml
class_map_version: "2.0"
classes: {car: 0, motorcycle: 1, pedestrian: 2}

motorcycle_blueprints:      # CARLA 0.9.16
  - vehicle.harley-davidson.low_rider
  - vehicle.kawasaki.ninja
  - vehicle.yamaha.yzf
  - vehicle.vespa.zx125

pedestrian_blueprints:
  - "walker.pedestrian.*"

bicycle_blueprints:         # 不生成；若出现则 ignore
  - vehicle.bh.crossbike
  - vehicle.diamondback.century
  - vehicle.gazelle.omafiets

# 其余 vehicle.* → car，并写 subtype（sedan/suv/van/bus/truck/emergency）
# 未在表内的蓝图 ID → 写入 unknown_blueprints.csv 并中止该序列，禁止静默归类
```

第一步动作：连上 CARLA 跑一遍导出实际蓝图清单，核对上表，**再**开始重采。

## 7. 落地步骤

### 7.1 阶段一：单序列打通（1–2 天）

1. 导出 CARLA 实际蓝图清单，定稿 §6.3 映射表；
2. 修 `labels.py`：三类别 + `blueprint_id` + `subtype` + `category_id`；
3. 加 `sensor.camera.instance_segmentation`（640×360 即可）计算 `visibility` / `visible_bbox` / `occluded`，事件仍在全分辨率；
4. **新增 `snapshot.json` 落盘**（位姿 + 蓝图 + 3D 框 + 可见像素数），投影改为离线脚本；
5. 修 D5 的截断判定；
6. 跑 1 条序列，用三栏可视化人工确认：骑手不重复标行人、树后无框、三类别计数正确。

**验收**：单序列中 motorcycle / pedestrian 各有 ≥ 20 条真实运动轨迹；重叠框未合并；被遮挡目标 `visibility < 0.2`。

### 7.2 阶段二：场景与批量（3–5 天）

1. 改 `traffic.py`（§6.1、§6.2）；
2. 采集参数改 40 Hz；
3. RGB 改存 JPEG q=90（见 §8）；
4. 批量跑 20–30 个路口 × 2 时段 × 2 天气；
5. 输出 `unknown_blueprints.csv`、低事件清单、拥挤场景清单。

### 7.3 阶段三：离线后处理（2–3 天）

1. 事件统计脚本（numpy 向量化，单序列分钟级）；
2. `quality_flags` 按 §5.2 判定表写入；
3. 三栏质检视频（RGB / 事件帧 / 统计+报警）；
4. 自动检查 6 项：
   - 事件时间戳严格递增、坐标极性合法；
   - bbox 有限值、宽高 > 0、不越界；
   - 同 actor 同帧不重复；
   - 帧内事件区间与 `event_offsets` 一致；
   - 相邻帧轨迹位移/尺寸突变报警；
   - `ignore` 样本未被当成普通背景。

### 7.4 阶段四：划分与加载器（1–2 天）

1. 按**路口**划分（不是按序列随机分——同路口不同序列外观高度相似，会造成泄漏）；
2. 测试集留出未见过的路口 + 至少 1 个夜间序列；
3. 加载器按"单窗口多实例"读取，`difficult` 是否参与训练由配置控制。

### 7.5 数据规模建议

近 5 个路口不足以训练三类别检测器。建议目标：

| 维度 | 当前 | 目标 |
|---|---|---|
| 路口 | 5 | ≥ 30（Town10HD_Opt 有大量信号灯杆，`plan_rig.py` 可批量生成） |
| 机位序列 | 10 | ≥ 100 |
| 行人轨迹（真实运动） | ~0 | ≥ 5 000 |
| 摩托车实例 | 0 | ≥ 300 000 |
| 天气/时段覆盖 | 白天 4 + 夜间 1 | 每种 ≥ 10 条 |
